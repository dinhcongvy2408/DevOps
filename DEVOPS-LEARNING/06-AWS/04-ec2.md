## 1. Mục tiêu bài học

Sau bài này, bạn có thể:

- Giải thích **EC2 instance** là gì: một máy ảo chạy trên hypervisor của AWS, gắn vào một subnet trong VPC của bạn.
- Đọc được tên **instance type** (`t3.small` = họ `t`, thế hệ `3`, cỡ `small`). Hiểu cơ chế **CPU credit** của dòng burstable, và vì sao chế độ `unlimited` có thể phát sinh phí.
- Tìm **AMI Ubuntu 24.04** chính thức bằng SSM public parameter, không chọn bừa AMI trên Marketplace.
- Dùng **user data** để cài phần mềm lúc khởi động lần đầu. Biết đọc `/var/log/cloud-init-output.log` khi script lỗi.
- Phân biệt **stop / terminate / hibernate / reboot**, và biết cái gì **vẫn bị tính tiền** khi instance đã stop.
- Truy vấn **IMDSv2** bằng token, và giải thích hop limit 1 hay 2 quyết định container có lấy được credential của instance role hay không.
- Gắn **instance profile** (`taskhub-ec2-role`), rồi vào máy bằng **SSM Session Manager**, không cần mở port 22.
- Giải thích vì sao dự án `taskhub` chọn `t3.small`, bằng phép tính RAM cụ thể.

## 2. Tại sao DevOps Engineer cần kiến thức này?

| Tình huống thật | Kiến thức EC2 cần dùng |
|---|---|
| Triển khai `taskhub` lên cloud (dự án v2, tuần 12) | Chọn instance type, AMI, subnet, security group, IAM role, user data cài Docker |
| "Server chậm từ chiều nay, CPU chỉ 20% mà vẫn ì" | Instance burstable **hết CPU credit** ở chế độ `standard` sẽ bị giới hạn về mức baseline |
| "Tháng này hóa đơn EC2 cao bất thường dù máy rảnh" | Chế độ `unlimited` tính phí surplus credit, volume EBS và Elastic IP vẫn bị tính khi máy đã stop |
| "Tôi stop rồi start lại, giờ không SSH vào được" | Public IPv4 tự cấp **đổi** sau mỗi lần stop/start |
| Kiểm toán bảo mật: "Server có mở SSH ra Internet không?" | Session Manager thay cho SSH, security group không có port 22 |
| Sự cố bảo mật kiểu "SSRF đánh cắp credential từ metadata" | IMDSv2 bắt buộc token, chặn được kiểu tấn công này |
| Pipeline CD (v3) chạy lệnh deploy trên server | SSM Run Command dùng chung agent và role như Session Manager |

EC2 là dịch vụ AWS mà bạn sẽ đụng tới **nhiều nhất** ở vị trí Junior. Ngay cả khi công ty dùng Kubernetes (EKS) hay ECS, bên dưới vẫn là các EC2 instance mà bạn cần debug được.

## 3. Kiến thức nền tảng cần hiểu

### 3.1. Instance là "máy ảo của bạn trên máy thật của AWS"

Ở [Docker 01](../04-DOCKER/01-vm-vs-container-architecture.md) bạn đã phân biệt VM và container. **EC2 instance là một VM**. Nó có kernel riêng và chạy trên hypervisor (AWS Nitro) trong một máy chủ vật lý ở một **Availability Zone**. Bạn không thấy máy vật lý. Bạn chỉ chọn:

| Bạn chọn | Tương đương ngoài đời |
|---|---|
| **Instance type** (`t3.small`) | Cấu hình phần cứng: số vCPU, RAM, băng thông mạng |
| **AMI** (Amazon Machine Image) | Ổ cài hệ điều hành dựng sẵn (Ubuntu 24.04) |
| **EBS volume** | Ổ cứng gắn qua mạng, sống độc lập với máy |
| **Subnet** (trong VPC — [bài 03](03-vpc-networking.md)) | Cắm máy vào mạng LAN nào, ở AZ nào |
| **Security group** | Firewall stateful gắn vào card mạng của máy ([Networking 05](../02-NETWORKING/05-tcp-udp-ports-firewall.md)) |
| **IAM role** (qua instance profile) | "Thẻ nhân viên" cho phần mềm chạy trên máy gọi AWS API |
| **User data** | Script chạy một lần khi máy khởi động lần đầu |

### 3.2. Từ vựng cần nắm

- **vCPU**: một luồng (thread) của nhân CPU vật lý. `t3.small` có 2 vCPU, tức là 1 nhân với 2 luồng.
- **Burstable instance** (dòng T: `t3`, `t4g`…): giá rẻ vì bạn chỉ được dùng CPU ở mức **baseline** (ví dụ 20%). Muốn vượt mức đó phải tiêu **CPU credit**.
- **EBS** (Elastic Block Store): ổ đĩa khối gắn qua mạng. Khác với **instance store** là ổ gắn trực tiếp trên máy vật lý, mất dữ liệu khi stop.
- **Instance profile**: "vỏ bọc" chứa một IAM role để gắn vào EC2. Console tạo tự động khi bạn tạo role cho EC2. CLI phải tạo riêng.
- **IMDS** (Instance Metadata Service): một HTTP server đặc biệt ở `169.254.169.254`, chỉ instance gọi được. Nó trả về instance ID, IP, user data và **credential tạm thời của IAM role**.
- **cloud-init**: chương trình trên Ubuntu đọc user data từ IMDS và chạy nó lúc boot lần đầu.

## 4. Giải thích chi tiết

### 4.1. 🟥 Đọc tên instance type

```text
 t   3   .  small
 │   │      └── cỡ: nano < micro < small < medium < large < xlarge < 2xlarge …
 │   └──────── thế hệ (số càng lớn càng mới)
 └──────────── họ: t = burstable (đa dụng, giá rẻ), m = đa dụng ổn định,
                   c = nặng CPU, r = nặng RAM, g/p = GPU…
 Hậu tố tùy chọn: g = CPU Graviton (ARM), a = AMD, i = Intel, flex = biến thể giá rẻ hơn
```

Theo tài liệu EC2, với tài khoản tạo **từ 15/07/2025** trở đi, các type đánh dấu *Free Tier eligible* là: `t3.micro`, `t3.small`, `t4g.micro`, `t4g.small`, `c7i-flex.large`, `m7i-flex.large`. Lưu ý quan trọng: với tài khoản kiểu mới này, "eligible" **không** có nghĩa là miễn phí 750 giờ như trước. Mọi giờ chạy đều **trừ vào credit** của Free plan (xem [bài 00](00-aws-account-setup-cost-safety.md)). Kiểm tra danh sách thật trên tài khoản của bạn:

```bash
# [WSL]
aws ec2 describe-instance-types \
    --filters Name=free-tier-eligible,Values=true \
    --query "InstanceTypes[*].[InstanceType]" \
    --output text | sort
```

`t4g` dùng CPU ARM (Graviton). Image `taskhub` hiện chỉ build cho `amd64` ([Docker 08](../04-DOCKER/08-container-troubleshooting.md) có lỗi `exec format error` khi chạy sai kiến trúc). Vì vậy dự án dùng họ **`t3`** (Intel, amd64).

### 4.2. 🟥 CPU credit: baseline, `standard` và `unlimited`

Bảng credit trong tài liệu EC2 (trích):

| Type | vCPU | RAM | Credit kiếm được/giờ | Credit tích tối đa | Baseline mỗi vCPU |
|---|---|---|---|---|---|
| `t3.micro` | 2 | 1 GiB | 12 | 288 | 10% |
| `t3.small` | 2 | 2 GiB | 24 | 576 | 20% |

**1 CPU credit = 1 vCPU chạy 100% trong 1 phút.** `t3.small` kiếm 24 credit/giờ, chia cho 2 vCPU và 60 phút thì ra 20%. Nghĩa là bạn dùng trung bình **20% mỗi vCPU** thì không hao credit.

Khi dùng vượt baseline, hai chế độ xử lý khác nhau:

| Chế độ | Khi hết credit tích lũy | Chi phí |
|---|---|---|
| `standard` | CPU bị **hạ xuống baseline** (máy chậm hẳn) | Không phát sinh thêm |
| `unlimited` | Tiếp tục chạy nhanh, tiêu **surplus credit** | Nếu trung bình 24 giờ vượt baseline thì **tính thêm phí** theo vCPU-giờ (trang giá ghi $0,05/vCPU-giờ cho T2/T3 Linux) |

⚠️ **Theo tài liệu EC2, T3 khởi chạy ở chế độ `unlimited` theo mặc định.** Trên Free plan, phí surplus trừ vào credit. Khi đã lên Paid plan, nó thành tiền thật. Một vòng lặp lỗi chiếm 100% CPU cả tuần có thể làm bạn mất tiền trong im lặng. Với lab học tập, bài này chủ động chọn **`standard`** (`--credit-specification CpuCredits=standard`): thà máy chậm còn hơn mất tiền. Bạn sẽ đo credit bằng CloudWatch metric `CPUCreditBalance` ở [bài 10](10-cloudwatch.md).

> Credit của T3 **được giữ 7 ngày** sau khi stop (theo tài liệu). Credit của T2 thì mất ngay khi stop.

### 4.3. 🟥 AMI: lấy đúng Ubuntu 24.04 của Canonical

Trên Marketplace có rất nhiều AMI tên "Ubuntu". Một số là bản do bên thứ ba đóng gói lại, có thể kèm phí hoặc phần mềm lạ. Cách chắc chắn nhất là hỏi **SSM public parameter** do Canonical công bố. Định dạng theo tài liệu Ubuntu:

```text
/aws/service/canonical/ubuntu/{product}/{release}/stable/{serial}/{arch}/hvm/{vol}/ami-id
                               server     24.04             current  amd64       ebs-gp3
```

```bash
# [WSL] — AMI ID mới nhất của Ubuntu Server 24.04 amd64, ổ gp3, ở region hiện tại
aws ssm get-parameter \
    --name /aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id \
    --query Parameter.Value --output text
```

Một vài điểm cần nắm:

- AMI ID **khác nhau theo region**, và Canonical cập nhật AMI thường xuyên (bản vá bảo mật). Đừng hard-code `ami-xxxx` vào tài liệu. Hãy hard-code **đường dẫn parameter**.
- AMI mặc định cho đăng nhập bằng user **`ubuntu`** (nếu dùng SSH). Session Manager thì dùng user `ssm-user`.
- Kiểm tra tên thiết bị gốc (root device) trước khi chỉnh cỡ ổ: `aws ec2 describe-images --image-ids <ami> --query 'Images[0].RootDeviceName'`.

### 4.4. 🟨 Key pair — chỉ cần nếu dùng SSH

EC2 hỗ trợ key **RSA 2048-bit** và **ED25519** (ED25519 chỉ dùng cho Linux). Dự án dùng **Session Manager** nên **không cần key pair**. Nếu muốn thử SSH ([Linux 05](../01-LINUX/05-packages-ssh.md)), hãy tự tạo key trên máy rồi import public key lên EC2, như vậy private key không bao giờ rời laptop:

```bash
# [WSL]
ssh-keygen -t ed25519 -f ~/.ssh/taskhub-lab -C "taskhub-lab"
aws ec2 import-key-pair --key-name taskhub-lab \
    --public-key-material fileb://$HOME/.ssh/taskhub-lab.pub
```

### 4.5. 🟥 User data và cloud-init

Theo tài liệu EC2:

- Shell script trong user data phải bắt đầu bằng `#!` (ví dụ `#!/bin/bash`). Script **chạy bằng root** (không dùng `sudo` bên trong) và **không tương tác**, nên mọi lệnh `apt-get install` phải có `-y`.
- Mặc định script **chỉ chạy ở lần boot đầu tiên**. Sửa user data rồi stop/start sẽ **không** chạy lại.
- Giới hạn **16 KB** (dạng thô, trước base64).
- Output của script nằm ở **`/var/log/cloud-init-output.log`**. Đây là chỗ đầu tiên cần đọc khi "user data không chạy".

Áp dụng bài học [Linux 06](../01-LINUX/06-bash-scripting.md) vào user data: luôn có `set -euxo pipefail`. Cờ `-x` in từng lệnh ra log, giúp bạn biết script chết ở dòng nào.

```bash
#!/bin/bash
set -euxo pipefail
apt-get update
apt-get install -y nginx
echo "<h1>taskhub lab04 - $(hostname)</h1>" > /var/www/html/index.html
systemctl enable --now nginx
```

⚠️ **User data không phải chỗ để secret.** Bất kỳ ai có quyền `ec2:DescribeInstanceAttribute`, hoặc bất kỳ process nào trên máy gọi được IMDS, đều đọc được nó. Mật khẩu PostgreSQL của `taskhub` lấy từ Parameter Store (v2), không bao giờ nằm trong user data.

### 4.6. 🟥 EBS: ổ đĩa sống tách khỏi máy

| Thuộc tính | Chọn cho `taskhub` | Lý do |
|---|---|---|
| Loại volume | **gp3** | SSD đa dụng thế hệ mới. Hiệu năng cơ bản cố định, không phụ thuộc dung lượng như gp2 |
| Dung lượng | **20 GiB** | Ubuntu (~2–3 GiB) + Docker image (~1 GiB) + dữ liệu PostgreSQL + log. Dư một chút để không đầy ổ ([Linux 07](../01-LINUX/07-logs-monitoring-troubleshooting.md)) |
| Mã hóa | **Bật** (`Encrypted=true`) | Không tốn thêm phí khi dùng khóa do AWS quản lý. Là yêu cầu bảo mật cơ bản |
| `DeleteOnTermination` | `true` cho root volume (mặc định) | Theo tài liệu, khi terminate thì root volume bị xóa, còn volume gắn thêm được giữ lại |

⚠️ Hệ quả của `DeleteOnTermination=true`: **dữ liệu PostgreSQL trong volume `pgdata` (nằm trên root volume) mất theo máy khi terminate**. Đó là lý do v5 có backup `pg_dump` lên S3 ([bài 05](05-s3.md)). Ngược lại, volume để `DeleteOnTermination=false` sẽ **tiếp tục bị tính tiền** sau khi máy đã terminate. Đây là một trong những khoản phí "quên" phổ biến nhất.

### 4.7. 🟥 Vòng đời instance và tiền

```text
            launch
              │
              ▼
          pending ──► running ──stop──► stopping ──► stopped ──start──► pending
                         │  ▲                                    
                  reboot │  │ (cùng máy vật lý, giữ IP)          
                         └──┘                                    
                         │ terminate                             
                         ▼                                       
                  shutting-down ──► terminated (không quay lại được)
```

Tóm tắt từ tài liệu EC2 (*Instance state changes*):

| Hành động | Tiền instance | Public IPv4 tự cấp | Elastic IP | Root EBS | Dữ liệu RAM |
|---|---|---|---|---|---|
| **Reboot** | Tiếp tục tính | Giữ nguyên | Giữ | Giữ | Mất |
| **Stop** | Ngừng tính | **Bị thu hồi. Start lại sẽ nhận IP mới** | Vẫn gắn, **vẫn tính tiền** | Giữ, **vẫn tính tiền lưu trữ** | Mất |
| **Hibernate** | Tính trong lúc `stopping`, ngừng khi `stopped` | Như stop | Như stop | Giữ (kèm file RAM) | Lưu xuống EBS |
| **Terminate** | Ngừng tính | Mất | Bị gỡ ra (EIP còn trong tài khoản thì **vẫn tính tiền**) | Bị xóa (mặc định) | Mất |

Ba điều rút ra cho túi tiền của bạn:

1. **Stop không có nghĩa là $0.** EBS vẫn tính tiền theo GB-tháng.
2. **Elastic IP** (IP tĩnh) bị tính tiền **dù đang gắn hay đang rảnh**. Trang giá EC2 ghi rõ: *"All In-use and Idle Elastic IP addresses are charged"*. Giá Public IPv4 là $0,005/giờ mỗi địa chỉ (trang giá VPC). Dự án không dùng EIP mặc định. Chấp nhận IP đổi khi stop/start, và [bài 09](09-route53.md) bàn cách xử lý bằng DNS.
3. Mỗi lần chuyển từ `stopped` sang `running` bị tính **tối thiểu 1 phút**.

**Termination protection** (`DisableApiTermination`): bật lên thì console/CLI/API không terminate được máy cho đến khi tắt nó đi. Nên bật cho instance `taskhub-app` của v2 để tránh tay lỡ bấm nhầm.

### 4.8. 🟥 IMDSv2 — metadata có khóa

IMDS trả về cả **credential tạm thời của IAM role** gắn với máy. Ở IMDSv1, một request `GET` đơn giản là đủ. Nếu ứng dụng web có lỗi **SSRF** (kẻ tấn công khiến server gọi một URL tùy ý), kẻ đó chỉ cần yêu cầu server gọi `http://169.254.169.254/latest/meta-data/iam/security-credentials/...` là lấy được credential.

**IMDSv2** bắt buộc làm hai bước:

```bash
# [EC2] Bước 1: xin token bằng PUT (SSRF thông thường chỉ làm được GET)
TOKEN=$(curl -sS -X PUT "http://169.254.169.254/latest/api/token" \
          -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
# Bước 2: dùng token trong header
curl -sS -H "X-aws-ec2-metadata-token: $TOKEN" \
     http://169.254.169.254/latest/meta-data/instance-id
```

Theo tài liệu EC2, khi bạn chọn **V2 only (token required)**:

- Tham số CLI tương ứng là `HttpTokens=required`. Request không có token sẽ bị từ chối (HTTP 401).
- **Hop limit** (`HttpPutResponseHopLimit`) là số "bước nhảy" mạng mà gói tin trả lời token được phép đi qua. Mặc định là 1 nếu AMI không khai báo `ImdsSupport: v2.0`. Container chạy trong bridge network của Docker đứng sau thêm **một hop** (gói tin đi qua `docker0`), nên với hop limit 1 container không nhận được token. **AWS khuyến nghị đặt 2 cho môi trường container** — khi container **cần** gọi AWS bằng quyền của instance role. Container của `taskhub` thì **không** cần: app không gọi API AWS nào, còn driver log `awslogs` chạy trong `dockerd` trên host (không đi qua `docker0`). Vì vậy dự án cố ý đặt `HttpPutResponseHopLimit=1`: nếu kẻ tấn công chiếm được container, họ **không** lấy được credential của `taskhub-ec2-role`. Đây là quyền tối thiểu áp dụng cho mạng. Chỉ nâng lên 2 khi có container thật sự cần quyền AWS (bài tập 4 cho bạn thấy sự khác biệt).

> 🟨 Hop limit 2 nghĩa là container **cũng** đọc được credential của role. Đó là đánh đổi có ý thức: role `taskhub-ec2-role` được thiết kế quyền tối thiểu ([bài 02](02-iam.md)), nên lộ cũng không lấy được nhiều. Ở mức nâng cao, có thể chặn container tới IMDS bằng iptables.

Tài khoản có thể đặt IMDSv2 là mặc định cho mọi instance mới, theo từng region. Phần [bài tập 3](#14-bài-tập-tự-làm) yêu cầu bạn tìm và bật thiết lập này.

### 4.9. 🟥 Instance profile và Session Manager

**Vì sao không SSH?**

| | SSH | Session Manager |
|---|---|---|
| Port mở trên security group | 22 (inbound) | **Không có port inbound nào** |
| Xác thực | Private key (có thể bị lộ, copy, quên thu hồi) | IAM user + MFA của bạn |
| Ghi lại ai làm gì | Phải tự cấu hình | Có thể ghi log phiên vào CloudWatch/S3 |
| Khi IP nhà bạn đổi | Phải sửa rule `<ip>/32` | Không ảnh hưởng |

Session Manager cần **ba điều kiện**, và đây cũng là ba chỗ hỏng phổ biến nhất:

1. **SSM Agent đang chạy trên máy.** Tài liệu Systems Manager ghi: agent được **cài sẵn** trên AMI Ubuntu Server 24.04 (bản AMI từ 20180627 trở đi), dưới dạng **snap**. Kiểm tra bằng `sudo snap services amazon-ssm-agent`.
2. **Máy có quyền nói chuyện với Systems Manager.** Instance profile chứa role có policy AWS managed **`AmazonSSMManagedInstanceCore`**. Trong dự án, đó là `taskhub-ec2-role` tạo ở [bài 02](02-iam.md).
3. **Máy đi ra được Internet tới các endpoint** `ssm.<region>.amazonaws.com`, `ssmmessages.<region>.amazonaws.com` và `ec2messages.<region>.amazonaws.com` qua **HTTPS 443 outbound**. Hai cách đáp ứng: máy ở public subnet **có Public IPv4** và route tới Internet Gateway (dự án chọn cách này), hoặc tạo **VPC interface endpoint** (tính phí theo giờ, không dùng trong dự án). Máy ở private subnet không có NAT và không có endpoint thì **không bao giờ** hiện trong Session Manager.

Mở phiên:

- `[AWS Console]` EC2 → chọn instance → **Connect** → tab **Session Manager** → **Connect**.
- `[WSL]` 🟨 `aws ssm start-session --target i-0123456789abcdef0`. Cách này cần cài thêm **Session Manager plugin** trên WSL; xem link cài đặt trong phần nguồn tham khảo.

Phiên mở ra với user `ssm-user` (có quyền sudo). Dùng `sudo -i` hoặc `sudo -u ubuntu -i` tùy việc.

### 4.10. 🟨 EC2 Instance Connect và SSH hardening

**EC2 Instance Connect** đẩy một public key tạm thời (sống 60 giây) lên máy, rồi bạn SSH bằng key đó. Cách này vẫn cần port 22 mở, từ IP của bạn hoặc từ dải IP của dịch vụ. Biết để nhận ra khi gặp ở công ty. Dự án không dùng.

Nếu bắt buộc dùng SSH (ví dụ công ty chưa có SSM):

- Rule security group cho port 22 chỉ từ **`<IP-của-bạn>/32`**, **tạm thời**, và **xóa ngay** sau khi dùng. Lấy IP bằng `curl -s https://checkip.amazonaws.com`.
- Trong `/etc/ssh/sshd_config`: đặt `PasswordAuthentication no` và `PermitRootLogin no` (ôn lại [Linux 05](../01-LINUX/05-packages-ssh.md)).
- **Không bao giờ** mở `0.0.0.0/0` cho port 22. Bot quét Internet sẽ tìm thấy máy trong vài phút.

### 4.11. 🟨 Status check và Service Quotas

**Status check** (chạy mỗi phút, tài liệu EC2):

| Loại | Phát hiện | Ai sửa | Metric CloudWatch |
|---|---|---|---|
| System | Lỗi hạ tầng AWS: mất điện, mất mạng, lỗi máy vật lý | AWS. Bạn có thể stop/start để chuyển sang máy khác | `StatusCheckFailed_System` |
| Instance | Lỗi trong máy của bạn: cấu hình mạng sai, **hết RAM**, filesystem hỏng, kernel không khớp | **Bạn** | `StatusCheckFailed_Instance` |
| Attached EBS | Volume EBS gắn vào máy không I/O được | AWS / bạn thay volume | `StatusCheckFailed_AttachedEBS` |

[Bài 10](10-cloudwatch.md) đặt alarm trên `StatusCheckFailed`.

**Service Quotas (vCPU):** số instance On-Demand bị giới hạn theo **tổng vCPU đang chạy** trong mỗi region. Quota *Running On-Demand Standard (A, C, D, H, I, M, R, T, Z) instances* (mã `L-1216C47A`) có giá trị mặc định ghi trong tài liệu là **5 vCPU**. Tài khoản rất mới có thể còn thấp hơn. Mỗi `t3.small` chiếm 2 vCPU, nên **tối đa 2 cái chạy cùng lúc** với quota 5. Instance ở trạng thái stopped không tính vào quota. Kiểm tra:

```bash
# [WSL]
aws service-quotas get-service-quota --service-code ec2 --quota-code L-1216C47A \
    --query 'Quota.Value'
```

Vượt quota thì `run-instances` báo lỗi `VcpuLimitExceeded`. Cách xử lý: terminate máy thừa, hoặc gửi yêu cầu tăng quota trong Service Quotas console.

### 4.12. 🟥 Vì sao `taskhub` chọn `t3.small` — làm phép tính

Stack v2 trên một máy gồm: Ubuntu + Docker + `nginx` + `taskhub` (JVM) + `postgres:17`.

| Thành phần | RAM ước tính | Cơ sở |
|---|---|---|
| Ubuntu + systemd + snapd + SSM Agent + dockerd/containerd | ~350–450 MiB | Đo bằng `free -m` sau khi boot (bạn sẽ tự đo ở lab) |
| `nginx:1.30-alpine` | ~10–20 MiB | Rất nhẹ |
| `postgres:17` (dữ liệu nhỏ) | ~100–200 MiB | `shared_buffers` mặc định 128 MB + các process con |
| `taskhub` (Spring Boot, JVM) | Heap + ~150–250 MiB ngoài heap (metaspace, thread stack, code cache) | Dockerfile dùng `-XX:MaxRAMPercentage=75.0` |

Điểm mấu chốt nằm ở `MaxRAMPercentage=75.0`. JVM tính 75% **của giới hạn RAM mà nó thấy**:

- **Container có `mem_limit: 768m`**: heap tối đa ≈ 576 MiB, cộng phần ngoài heap ≈ 750 MiB. Tổng cả máy ≈ 450 + 20 + 200 + 750 ≈ **1,4 GiB**, vừa với **2 GiB** của `t3.small` và còn chỗ cho page cache.
- **Container không có giới hạn RAM**: JVM thấy **toàn bộ RAM của máy** và cho heap tới 75% × 2 GiB = 1,5 GiB. Chỉ riêng `taskhub` đã có thể chiếm gần hết máy, PostgreSQL bị kernel OOM-kill ([Docker 01](../04-DOCKER/01-vm-vs-container-architecture.md) — exit 137). Vì vậy compose production nên đặt giới hạn RAM cho `taskhub` ([Docker 07 — checklist mục 8](../04-DOCKER/07-docker-security.md)).
- **`t3.micro` (1 GiB)**: 450 + 20 + 200 = 670 MiB trước khi có JVM, chỉ còn ~350 MiB cho Spring Boot. Không đủ, trừ khi thêm swap và chấp nhận chậm. Đó là lý do không chọn.

Cách tra giá `t3.small` ở Singapore (không ghi cứng con số vì giá có thể đổi):

- `[Trình duyệt]` [AWS Pricing Calculator](https://calculator.aws/) → Add service → EC2 → region *Asia Pacific (Singapore)* → `t3.small`, Linux, On-Demand, 730 giờ/tháng.
- 🟦 `[WSL]` Price List API (endpoint ở `us-east-1`):

  ```bash
  aws pricing get-products --region us-east-1 --service-code AmazonEC2 \
      --filters Type=TERM_MATCH,Field=instanceType,Value=t3.small \
                Type=TERM_MATCH,Field=regionCode,Value=ap-southeast-1 \
                Type=TERM_MATCH,Field=operatingSystem,Value=Linux \
                Type=TERM_MATCH,Field=tenancy,Value=Shared \
                Type=TERM_MATCH,Field=preInstalledSw,Value=NA \
                Type=TERM_MATCH,Field=capacitystatus,Value=Used \
      --query 'PriceList[0]' --output text | grep -o '"USD":"[0-9.]*"'
  ```

Ghi con số tra được vào `docs/cost.md` của dự án. Nhân với 730 giờ để biết chi phí một tháng nếu chạy 24/7, và so với credit còn lại.

## 5. Ví dụ thực tế

**Tình huống 1 — "Server ì ạch mỗi chiều".** Một công ty chạy CI agent trên `t3.medium` ở chế độ `standard`. Buổi sáng build nhanh. Chiều, sau nhiều lượt build liên tục, `CPUCreditBalance` về 0 và CPU bị hạ xuống baseline 20%, nên mỗi build chậm gấp 3–4 lần. Đồ thị `CPUUtilization` dừng phẳng ở đúng mức baseline là dấu hiệu nhận biết. Cách xử lý: chuyển sang `unlimited` (chấp nhận phí) hoặc đổi sang họ `m`/`c` có CPU cố định.

**Tình huống 2 — "Hóa đơn tháng có 30 USD tiền EBS dù đã xóa hết máy".** Một bạn tạo 3 instance thử nghiệm, mỗi cái có thêm một volume dữ liệu 100 GiB với `DeleteOnTermination=false`. Terminate máy xong, volume vẫn còn ở trạng thái `available` và tiếp tục bị tính tiền. Bài học: checklist dọn dẹp luôn có lệnh `aws ec2 describe-volumes --filters Name=status,Values=available`.

**Tình huống 3 — Capital One 2019 (sự cố công khai).** Kẻ tấn công lợi dụng lỗi SSRF qua một WAF cấu hình sai để đọc credential IAM từ instance metadata, rồi tải dữ liệu từ S3. Sau sự cố này AWS ra mắt IMDSv2 (cuối 2019). Ngày nay IMDSv2 là thiết lập tối thiểu.

## 8. Giải thích câu lệnh và tham số

### 8.1. `aws ec2 run-instances`

```bash
# [WSL] ⚠️ TẠO TÀI NGUYÊN TÍNH PHÍ
aws ec2 run-instances \
    --image-id "$AMI_ID" \
    --instance-type t3.small \
    --subnet-id "$SUBNET_ID" \
    --security-group-ids "$SG_ID" \
    --associate-public-ip-address \
    --iam-instance-profile Name=taskhub-ec2-role \
    --metadata-options "HttpEndpoint=enabled,HttpTokens=required,HttpPutResponseHopLimit=1" \
    --credit-specification CpuCredits=standard \
    --block-device-mappings "DeviceName=${ROOT_DEV},Ebs={VolumeSize=20,VolumeType=gp3,Encrypted=true,DeleteOnTermination=true}" \
    --user-data file://userdata-lab04.sh \
    --tag-specifications \
      'ResourceType=instance,Tags=[{Key=Name,Value=taskhub-lab04},{Key=Project,Value=taskhub},{Key=Env,Value=dev},{Key=Owner,Value=phuong},{Key=ManagedBy,Value=manual}]' \
      'ResourceType=volume,Tags=[{Key=Name,Value=taskhub-lab04-root},{Key=Project,Value=taskhub},{Key=Env,Value=dev},{Key=Owner,Value=phuong},{Key=ManagedBy,Value=manual}]' \
    --query 'Instances[0].InstanceId' --output text
```

| Tham số | Ý nghĩa | Nếu bỏ đi / sai |
|---|---|---|
| `--image-id` | AMI dùng để boot | Bắt buộc. AMI của region khác báo `InvalidAMIID.NotFound` |
| `--instance-type` | Cấu hình phần cứng | Mặc định là một type cũ. Luôn ghi rõ |
| `--subnet-id` | Subnet (và vì thế cả AZ, VPC) | Bỏ đi thì AWS dùng **default VPC**, không phải `taskhub-vpc` |
| `--security-group-ids` | Firewall | Bỏ đi thì dùng SG `default` của VPC |
| `--associate-public-ip-address` | Xin Public IPv4 cho card mạng chính | Thiếu (và subnet không bật auto-assign) thì máy không ra Internet, **không vào được Session Manager** |
| `--iam-instance-profile Name=...` | Gắn role vào máy | Thiếu thì máy không đăng ký được với SSM |
| `--metadata-options` | `HttpTokens=required`: bắt buộc IMDSv2. `HttpPutResponseHopLimit=1`: container (sau `docker0`) **không** lấy được token — taskhub không cần, nên chặn |  Mặc định có thể cho phép IMDSv1 (tùy thiết lập tài khoản/AMI) |
| `--credit-specification CpuCredits=standard` | Tắt chế độ `unlimited` | Mặc định của T3 là `unlimited` |
| `--block-device-mappings` | Cỡ, loại, mã hóa của root volume. `DeviceName` phải **đúng** tên root device của AMI | Sai `DeviceName` thì tạo ra **thêm** một volume trống thay vì chỉnh root volume |
| `--user-data file://...` | Script cloud-init. CLI tự mã hóa base64 | Quên `file://` thì CLI gửi **chuỗi đường dẫn** làm user data |
| `--tag-specifications` | Gắn tag cho instance **và** volume ngay lúc tạo | Thiếu tag thì khó tìm, khó dọn, khó phân bổ chi phí |
| `--query ... --output text` | Chỉ in instance ID | — |

### Bước 7 — IMDSv2 `[EC2]`

```bash
# IMDSv1 (không token) — phải bị từ chối
curl -s -o /dev/null -w '%{http_code}\n' http://169.254.169.254/latest/meta-data/instance-id   # 401

# IMDSv2
TOKEN=$(curl -sS -X PUT "http://169.254.169.254/latest/api/token" \
          -H "X-aws-ec2-metadata-token-ttl-seconds: 300")
for p in instance-id instance-type placement/availability-zone local-ipv4 public-ipv4 iam/info; do
  printf '%-32s ' "$p"; curl -sS -H "X-aws-ec2-metadata-token: $TOKEN" \
    "http://169.254.169.254/latest/meta-data/$p"; echo
done
```

Đầu ra mẫu (minh họa):

```text
401
instance-id                      i-0a1b2c3d4e5f67890
instance-type                    t3.small
placement/availability-zone      ap-southeast-1a
local-ipv4                       10.20.1.37
public-ipv4                      13.229.x.x
iam/info                         { "Code" : "Success", ... "InstanceProfileArn" : "arn:aws:iam::111122223333:instance-profile/taskhub-ec2-role", ... }
```

❓ Chạy thêm `curl -sS -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/iam/security-credentials/taskhub-ec2-role`. Bạn thấy gì? Viết 2 câu giải thích vì sao IMDSv2 và quyền tối thiểu của role quan trọng. **Không** dán kết quả này vào bất kỳ đâu.

Thoát phiên bằng `exit`.

## 10. Kết quả mong đợi

- `curl http://<PUBLIC_IP>/` từ WSL trả về `<h1>taskhub lab04 - ip-10-20-1-xx</h1>`. Từ IP khác thì timeout.
- Instance hiện `Online` trong `aws ssm describe-instance-information`, và vào được shell qua Session Manager mà **không** có rule port 22.
- `cloud-init status` là `done`. Log có các dòng `+ ...` do `set -x`.
- Gọi IMDS không token trả về **401**. Gọi có token thì trả về instance-id, AZ, IP.
- Sau stop/start: **Public IPv4 đổi**, private IP giữ nguyên, nginx tự chạy lại (do systemd), user data **không** chạy lại.
- `terminate-instances` bị chặn khi bật termination protection.
- Sau dọn dẹp: 4 lệnh kiểm tra đều cho kết quả rỗng hoặc `terminated`.
- File `week12/ec2-lab.md` có: hai Public IP, kết quả `free -m`, câu trả lời các câu hỏi ❓.

| Container gọi IMDS bị treo/timeout khi xin token | Hop limit = 1 (với taskhub đây là **thiết kế**; chỉ sửa nếu container thật sự cần quyền AWS) | `aws ec2 describe-instances --query '...MetadataOptions'` | `aws ec2 modify-instance-metadata-options --instance-id ... --http-put-response-hop-limit 2` |
| `terminate-instances` báo `OperationNotPermitted` | Termination protection đang bật | `describe-instance-attribute --attribute disableApiTermination` | Tắt protection rồi terminate (có chủ ý) |

## 12. Đọc log và xử lý lỗi

### 12.1. Quy trình khi "không vào được Session Manager"

Đi từ ngoài vào trong, mỗi bước loại trừ một tầng:

```text
1. Instance có running và status check OK không?
   aws ec2 describe-instance-status --instance-ids "$IID" --include-all-instances \
     --query 'InstanceStatuses[0].[InstanceState.Name,SystemStatus.Status,InstanceStatus.Status]'
2. Có instance profile chứa AmazonSSMManagedInstanceCore không?
   aws ec2 describe-instances --instance-ids "$IID" \
     --query 'Reservations[0].Instances[0].IamInstanceProfile.Arn'
   aws iam list-attached-role-policies --role-name taskhub-ec2-role
3. Máy có đường ra Internet không?
   - Có PublicIpAddress không? (describe-instances)
   - Route table của subnet có 0.0.0.0/0 → igw-... không? (bài 03)
   - SG/NACL outbound có cho 443 không?
4. Agent có chạy không? (không vào được máy thì đọc console output)
   aws ec2 get-console-output --instance-id "$IID" --latest --output text | tail -n 50
```

Bước 4 là cửa sổ duy nhất nhìn vào máy khi mọi cách kết nối đều hỏng. Console output chứa log boot và log cloud-init in ra console.

### 12.2. Đọc `cloud-init-output.log`

Ví dụ minh họa một user data hỏng vì gõ sai tên gói:

```text
+ apt-get update
Hit:1 http://ap-southeast-1.ec2.archive.ubuntu.com/ubuntu noble InRelease
...
+ apt-get install -y ngnix
Reading package lists...
E: Unable to locate package ngnix
2026-... - cc_scripts_user.py[WARNING]: Failed to run module scripts_user (scripts in /var/lib/cloud/instance/scripts)
```

Cách đọc:

1. Tìm dòng `+ ...` **cuối cùng**. Đó là lệnh chạy sau cùng trước khi `set -e` dừng script.
2. Đọc ngay dòng lỗi bên dưới nó (`E: Unable to locate package ngnix`).
3. Dòng `Failed to run module scripts_user` chỉ là **hệ quả**, cho biết user data thất bại. Nó không phải nguyên nhân.

Ghi lỗi vào `troubleshooting-journal.md` theo [mẫu](../00-ROADMAP/templates/troubleshooting-journal-template.md).

### 12.3. Đọc log SSM Agent `[EC2]`

```bash
sudo tail -n 50 /var/log/amazon/ssm/amazon-ssm-agent.log
sudo tail -n 50 /var/log/amazon/ssm/errors.log
```

Theo tài liệu, thư mục log là `/var/log/amazon/ssm`, kể cả khi agent cài bằng snap. Các thông báo kiểu "không lấy được credential" hoặc "Access denied" trỏ về **role**. Thông báo kiểu timeout khi kết nối tới `ssm.ap-southeast-1.amazonaws.com` trỏ về **mạng** (route, SG, NACL). *(Chữ chính xác thay đổi theo phiên bản agent. Hãy tìm từ khóa `credentials`, `AccessDenied`, `timeout`.)*

## 14. Bài tập tự làm

> Lời giải: [solutions/04-solutions.md](solutions/04-solutions.md). Hãy tự làm trước.

**Bài 1 — Đọc đúng cấu hình đang chạy.** Với một instance bất kỳ (chạy lại lab nếu cần), viết **một** lệnh `describe-instances` có `--query` in ra bảng gồm: instance ID, tên, AZ, chế độ IMDS (`HttpTokens`), hop limit, ARN instance profile, loại và cỡ root volume. Gợi ý: cỡ volume phải gọi thêm `describe-volumes`; hãy viết lệnh thứ hai.

**Bài 2 — User data hỏng có chủ đích.** Tạo instance với user data cài `ngnix` (sai chính tả). Chỉ dùng `get-console-output` và Session Manager, chứng minh nguyên nhân bằng đúng dòng log. Sau đó trả lời: sửa user data của instance đang chạy rồi stop/start thì có sửa được không? Vì sao? Nhớ dọn dẹp.

**Bài 3 — IMDSv2 mặc định cho cả region.** Tìm trong tài liệu EC2 cách đặt **IMDSv2 required + hop limit 2** làm mặc định cấp tài khoản cho `ap-southeast-1` (cả bằng console và CLI). Thực hiện, rồi chứng minh bằng `get-instance-metadata-defaults`. Giải thích thiết lập này **không** làm gì với instance đã tồn tại.

**Bài 4 — Container và hop limit.** Trên một instance có Docker (cài theo [tài liệu Docker cho Ubuntu](https://docs.docker.com/engine/install/ubuntu/)), chạy `docker run --rm curlimages/curl` để xin token IMDS với hop limit 1, rồi với hop limit 2 (dùng `modify-instance-metadata-options`). Ghi lại hiện tượng và giải thích bằng sơ đồ đường đi của gói tin. (Chạy xong nhớ terminate.)

**Bài 5 — Chi phí 1 tháng.** Tra giá `t3.small` Linux On-Demand ở Singapore (Pricing Calculator hoặc Price List API). Tính chi phí một tháng chạy 24/7 cho: instance + gp3 20 GiB + 1 Public IPv4. Rồi tính lại theo lịch học thực tế (ví dụ 3 giờ/ngày, các giờ còn lại stop). Ghi vào `docs/cost.md` kèm ngày tra giá. Kết luận: credit của bạn đủ cho bao nhiêu tháng với mỗi kiểu?

**Bài 6 — Runbook "không vào được máy".** Viết `docs/runbooks/ec2-cannot-connect.md` (tối đa 1 trang): các bước chẩn đoán theo thứ tự, lệnh dùng ở mỗi bước, và cách nhận ra từng nguyên nhân. Đây sẽ là runbook đầu tiên của dự án.

## 15. Tiêu chí đánh giá đã hiểu bài

- [ ] Giải thích được CPU credit bằng số liệu của `t3.small`, và nói được rủi ro chi phí của chế độ `unlimited`.
- [ ] Lấy được AMI Ubuntu 24.04 bằng SSM parameter mà không cần nhìn tài liệu.
- [ ] Tạo được instance có IMDSv2, hop limit 1 (và giải thích khi nào cần 2), role, tag, không key pair, không port 22. Giải thích được **từng** tham số của `run-instances`.

- [ ] Đọc `cloud-init-output.log` và chỉ ra đúng lệnh làm user data thất bại.

- [ ] Bảo vệ được lựa chọn `t3.small` bằng phép tính RAM, kể cả vai trò của `mem_limit` với `MaxRAMPercentage`.
